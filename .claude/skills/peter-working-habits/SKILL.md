# PeterChang 的工作習慣（摘要）

## 溝通
- 用台灣繁體中文回覆。
- 需求裡寫了「討論一／二／三」或「要有結論才能到下一步」時，每個關卡都停下來等結論，不要自己往下做。
- 提選項時給出建議和理由，不要只列清單；需要我決定的事再問，能用常理判斷的就直接做並說明。
- 長時間任務要主動回報進度，並告訴我怎麼自己看（例如 `tail -f` 哪個 log）。

## 做決策的方式
- 研究要回到原始資料（例如 HTTP Archive 原始資料表），寫清楚分母、樣本範圍和資料缺口，不用二手摘要的數字下結論。
- 優先選可擴充的架構（例如依覆蓋率分層），不做一次性的硬編碼。
- 需要付出成本的決策（例如多要瀏覽器權限）先量測問題的實際頻率，數據證明值得才做。
- 被質疑的地方要能防禦：樣本怎麼選、排除了誰、為什麼排除，都要能講清楚。

## 專案限制（ui_extension）
- l1：不用 popup.html / popup.js。
- l2：不能有資安漏洞，最小權限，不用 innerHTML、eval 這類寫法。
- l3：不硬編碼。ID、按鍵、屬性名稱、介面文字都從設定檔或 _locales 讀，測試也從設定檔取值。

## 驗證
- 設計規則要有對應的測試在把關。
- 自動化指標要用人工判斷驗證過才算數，並且盲測（不讓判斷的人看到指標結果）。
- 量測要列出排除漏斗，對量不到的真實網站做重試，並算出最壞情況的下限。
- 失敗照實說：測試沒過、流程卡住、自己的疏失都直接講，修正的是哪一邊（產品或測試）也要講清楚。

## docs/ 底下的文件
- 開頭用條列寫「作者：PeterChang」和「最後修改：YYYY-MM-DD HH:MM」，每次修改都更新時間。
- 寫給不懂技術的人也看得懂：化繁為簡，句子短，專有名詞要嘛用一句白話解釋、要嘛拿掉；完整方法放附錄。
- 重要的項目用條列式，並用顏色加粗體標出來：`<span style="color:#1a7f37"><b>…</b></span>`。顏色固定三種，文件開頭放一行說明：綠色 #1a7f37 是好消息或已完成，紅色 #cf222e 是問題或風險，藍色 #0969da 是關鍵數字或決定。只標真正重要的，不要每行都標。
- 讀起來要像我自己寫的：第一人稱、平實語氣；不用表情符號標記，表格只用在比較數字，避開「不只…而是…」「這正是…的價值」這類句型。
- 面試或給別人看的文件先講產品面：誰在用、解決什麼、放棄了什麼、怎麼衡量；工程細節放附錄。
- 區分「已驗證」和「待驗證的假設」，數字和事實不能因為改語氣而變動。
