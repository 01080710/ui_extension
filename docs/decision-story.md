# UIX：在客戶的網站上直接比稿，選好的風格直接交付

- 作者：PeterChang
- 最後修改：2026-10-12 01:43

顏色說明：<span style="color:#1a7f37"><b>綠色</b></span>是好消息或已完成，<span style="color:#cf222e"><b>紅色</b></span>是問題或風險，<span style="color:#0969da"><b>藍色</b></span>是關鍵數字或決定。

這份是我整理這個專案的決策紀錄，也是面試時的講稿。後面的附錄放技術細節，被問到再看。

先說清楚：<span style="color:#cf222e"><b>這個專案還沒有真實使用者</b></span>。寫「已驗證」的是我實際量過或測過的，寫「待驗證」的是還沒有資料支持的想法。

## 一分鐘版本

我是做資料工程的，最近常要接全端的案子。我發現案子卡住，常常不是程式寫不出來，而是<span style="color:#0969da"><b>客戶看不到東西，就沒辦法做決定</b></span>。畫設計稿要好幾天，客戶看的還是假畫面。

所以我做了一個 Chrome 擴充功能：

- 在客戶<b>自己的網站</b>上按一個鍵，就能切換 10 種設計風格
- 客戶選好以後，<b>直接匯出</b>成工程師能用的設定檔

我做決定都靠資料：

- 要先支援哪些網頁元件，我去撈了 <span style="color:#0969da"><b>3,000 萬個網頁</b></span>的原始資料，推翻了 4 個原本的猜測
- 上線前在 <span style="color:#0969da"><b>602 個真實網頁</b></span>上測試，<span style="color:#1a7f37"><b>九成能把風格完整套上去</b></span>
- 測試過程中，我發現<span style="color:#cf222e"><b>自己設計的檢查方法量錯了東西</b></span>，就把它拆成兩種

## 1. 問題是什麼

使用者是接案的工程師或 PM。他們的客戶常說「想要專業一點」「想要有現代感」，但說不出具體要什麼。

現在的做法都有缺點：

- <b>畫設計稿</b>：我估計要 1 到 3 天，還要來回改（待驗證，這是我的經驗）
- <b>給參考網站</b>：客戶想像不出放在自己網站上的樣子
- <b>直接改程式</b>：每試一種方向就要重做一次

## 2. 要解決的事

一句話：<span style="color:#0969da"><b>客戶說不出想要什麼時，直接在他的網站上給他看幾種方向，讓他用手指著選，選好就能交付。</b></span>

這可以拆成三步：探索、決定、交付。現有的工具都斷在某一步：

- 設計稿：探索很慢，看的是假畫面，最後還要再轉成程式
- Dark Reader 這類工具：只做深色模式，沒有東西可以交付
- 瀏覽器開發者工具：太技術，不能拿到客戶面前用

## 3. 我決定不做的事

- <span style="color:#0969da"><b>不跟 Dark Reader 搶「自己看得舒服」的市場</b></span>，專心做「幫客戶做決定」。深色、護眼這幾種風格還是保留，當作附加功能。
- <b>拿掉毛玻璃和新擬物兩種風格</b>：前者在很多網站上看不出效果，後者字天生不夠清楚。我想保證「任何網站都能拿來展示」，這兩種會破壞這個承諾。
- <span style="color:#0969da"><b>預設只換顏色</b></span>，改按鈕形狀的「強化模式」要另外打開。第一次用就把客戶網站弄壞，就不會有第二次。
- <b>權限能少就少</b>：安裝時跳出的權限越多，願意裝的人越少。一開始只要一個權限，後來多加的那一個，是先用資料證明值得才加的（見第 7 節）。
- <b>不用每次都要點開的彈出視窗</b>，改成按 U 叫出、按 I 收起，開會時可以一邊講一邊切。

## 4. 用原始資料決定要做什麼

這是我覺得最能代表我做事方式的一段。

一開始要決定先處理哪些網頁元件（按鈕、輸入框、彈出視窗等），第一版我參考的是網路文章的整理。我覺得不夠，<span style="color:#0969da"><b>要求每個元件都要有實際的使用比例才做決定</b></span>，於是直接去下載 HTTP Archive 的原始資料（3,000 萬個網頁）。

結果推翻了 4 個猜測（已驗證）：

- <span style="color:#cf222e"><b>彈出視窗</b></span>：標準寫法只有 0.3% 的網頁在用，另一種寫法卻有 31.5%，差了 100 倍。如果只照標準寫法處理，客戶網站上的彈出視窗幾乎都不會變。
- <b>展開收合</b>：一樣的狀況，3.5% 對 34%。
- <b>下拉選單、表格</b>：我原本以為很常見，實際只有 18% 左右，所以往後排。
- <b>勾選框和單選鈕</b>：原本想一起處理，實際是 24% 對 5%，所以分開看。

另一個發現：很多元件（卡片、標籤、提示框）每個網站的寫法都不一樣，沒有共通的標記。所以我只處理有共通寫法的元件，<span style="color:#0969da"><b>依照使用比例分成四層</b></span>，之後要加新元件，看比例放進對應的層就好。

我做資料工程的習慣是：二手整理常常漏掉「分母是什麼」，而結論對不對常常就看這個。

## 5. 怎麼確保它不出錯

每個對使用者的承諾，都有自動測試在檢查（已驗證：<span style="color:#1a7f37"><b>98 項單元測試、17 項實際操作瀏覽器的測試全部通過</b></span>）：

- <b>不會弄壞網站</b>：沒選風格時完全不影響網站；預設模式不改任何會讓版面移動的設定
- <b>每種風格都看得清楚</b>：10 種風格的文字和背景顏色，都有檢查對比夠不夠
- <b>選好就能交付</b>：三種匯出格式、10 種風格都有測試
- <b>不干擾工作</b>：Figma、Google 文件這類網站預設跳過
- <b>打中文不會誤觸</b>：用注音輸入時、在輸入框裡打字時，按 U 和 I 都不會觸發

## 6. 實際測試的結果

我在三組網站上測試：全球大網站、隨機抽的一般網站、台灣網站，每個網站看首頁和一個內頁，總共 602 頁（已驗證）。

- <span style="color:#1a7f37"><b>九成（90.0%）能把風格完整套上去</b></span>，最壞情況也有 81.6%
- <span style="color:#1a7f37"><b>大網站、一般網站、台灣網站表現差不多</b></span>
- <span style="color:#1a7f37"><b>套用後字更好讀</b></span>：清楚的文字從 85% 變成 99%

測試過程中，有四件事我覺得最值得講：

<b>第一，我發現自己的檢查方法量錯了東西。</b>
我自己用眼睛看了 43 張截圖，只有 1 張是真的壞掉。但自動檢查說有問題的，我看都沒壞；它說沒問題的那張，反而是真的壞掉了。原因是自動檢查只看「顏色有沒有換」，看不出「網站有沒有壞」。<span style="color:#0969da"><b>所以我把檢查拆成兩種</b></span>：自動檢查看完整度，人工檢查看有沒有壞。

<b>第二，量測工具本身也會作弊。</b>
被問到「打不開的網站怎麼辦」以後，我把每個打不開的網站都查了一遍，發現<span style="color:#cf222e"><b>是量測工具自己被大網站當成機器人擋掉</b></span>，還有一個連線順序的 bug 讓很多台灣網站被誤判。被擋掉的往往是設計最複雜的網站，等於只挑簡單的考。修好以後，<span style="color:#1a7f37"><b>多救回 94 個網站</b></span>。

<b>第三，差點用錯的數字做決定。</b>
要不要多要一個瀏覽器權限，我事先定好規則：查出來的原因超過六成是網站的強制寫法才做。第一次分析只有 42%，照規則不該做。但我覺得其中一類的比例高得不合理，回頭查才發現分析程式有 bug。<span style="color:#0969da"><b>修好後是 83%，結論完全相反。</b></span>

<b>第四，換字型會讓版面移動。</b>
預設模式雖然沒改任何版面設定，平均還是有三成的元素位置跑掉，原因是換了字型、字的寬度不同。<span style="color:#0969da"><b>所以我把換字型改成可以自己選要不要開</b></span>。

完整數字在 [coverage-report.md](coverage-report.md)。

## 7. 根據結果做的修正

- <span style="color:#1a7f37"><b>唯一一個「壞掉」的情況已經修好</b></span>：導覽列原本是深色時，現在會換成風格的品牌色，上面的白色圖示就不會消失
- <span style="color:#1a7f37"><b>換字型改成可選</b></span>，預設不換，版面就不會動
- 用 Shadow DOM 包起來的網頁元件，現在也會換顏色
- 新增 Alt+Shift+U 快捷鍵，不管游標在哪裡都能叫出面板
- <span style="color:#1a7f37"><b>匯出的檔案會記下來源</b></span>：風格、模式、哪個網站、什麼時候匯出、UIX 版本，之後才查得到「這份檔案是哪一次比稿產生的」。只記網站名稱，不記網址路徑，避免帶到私人資料
- 匯出多了「複製」按鈕，可以直接貼進專案
- <span style="color:#1a7f37"><b>網站的強制顏色也蓋得過去了</b></span>：先查了 20 個網頁，確認 83% 換不掉的字是網站用了強制寫法，達到我事先定的六成門檻，才決定多要一個權限去處理。改完後，原本 10 種風格只過 0 到 1 種的網站變成 10 種全過
- <span style="color:#cf222e"><b>還沒修的</b></span>：深色風格下，網站寫死成深色的圖示會看不見

## 8. 接下來要驗證的事

這些還是想法，沒有資料（待驗證）：

- <b>現場比稿是不是比較快</b>：在 5 場真實的客戶會議試用，看能不能在 30 分鐘內決定風格
- <b>匯出的設定檔會不會真的被用</b>：目標是一半以上會被放進正式專案
- <b>會不會弄壞網站</b>：加上使用者回報，目標是壞掉的回報低於 5%；人工檢查也要找第二個人一起看
- <b>大家是不是其實拿來閱讀</b>：如果深色、護眼風格用的人最多，就要重新想定位

## 可能被問的問題

<b>為什麼不直接用 Dark Reader？</b>
它解決的是「我自己看得舒服」，我要解決的是「讓客戶做決定，而且能交付」。

<b>怎麼知道這個產品有用？</b>
還不知道，因為還沒有真實使用者。目前證明的是「技術上做得到」，使用者需不需要，第 8 節是我的驗證計畫。

<b>九成是怎麼算的？</b>
一個網頁在某個風格下，九成五以上的文字顏色有換成功、而且看得清楚，才算成功。我也試過把門檻改鬆或改嚴，結果是 94% 和 82%，都列在報告裡。

<b>有用 AI 嗎？</b>
有，程式和調查是我和 AI 一起做的。產品方向、要做給誰用、每個階段要討論到有結論才往下、要求回到原始資料、要求檢查被排除的網站，這些是我決定的。

## 附錄 A：決策時間線

1. 先定三條規則：不用彈出視窗、不能有資安漏洞、不能把設定寫死在程式裡
2. 10 種風格抽象成 16 個參數，換風格只是換一組數字
3. 回到 3,000 萬網頁的原始資料，推翻 4 個猜測
4. 選「依使用比例分層」，不硬挑 10 個元件，方便以後擴充
5. 每條設計規則都寫成自動測試
6. 加做匯出、量測、網站例外清單、多語系、跟系統深淺色、跨瀏覽器
7. 測試範圍從大網站擴大成三組，再加上內頁
8. 人工檢查發現自動檢查量錯東西，拆成兩種
9. 找出量測工具被擋、連線誤判的問題，救回 94 個網站
10. 修好白色圖示消失、換字型改成可選、支援 Shadow DOM 和快捷鍵
11. 查 20 個網頁確認原因後，才決定多要權限處理網站的強制顏色（差點被分析程式的 bug 誤導）

## 附錄 B：技術細節（被追問時用）

- 權限：`storage`，加上為了 C1 的 `scripting`；網站存取範圍和原本 content script 的範圍完全一樣，有測試檢查不能變大
- C1：同一份 CSS 再用 `chrome.scripting.insertCSS` 以 USER origin 注入，使用者層級的 `!important` 會贏過網站所有的 `!important`（包括寫在元素上的）
- 沒選風格時，所有 CSS 規則都不會生效（每條規則都必須以 `html[data-uix-theme` 開頭，有測試檢查）
- 對比度標準：文字 WCAG AA 4.5 : 1，圖示 3 : 1
- 重置規則用 `:where()` 壓低權重，元件規則一定蓋得過；邊框用 `box-shadow: inset` 畫，不影響版面
- 置頂的 header、聊天視窗會被標記並保留不透明背景；原本是深色的導覽列會先量原始顏色，再換成品牌色
- 鍵盤：輸入框裡、注音組字中（keyCode 229）、按著修飾鍵時都不觸發
- 讀進來的設定一律當成不可信資料，逐欄驗證
- 同一份程式碼建出 Chrome、Edge、Firefox 三個版本
- 量測：每頁 90 秒上限、可以中斷後接著跑；信賴區間用重抽法計算；人工檢查和自動檢查的一致程度 Cohen's κ = −0.04
